# M2: GPUI runs inside the engine on Windows, 2026-11-10

Chromium 156.0.8078.88 plus jaal's layer (`engine/src/jaal`) and six small patches, with the UI library on GPUI (`crates/jaal-ui`) loaded into the browser process. Built and run on the Windows laptop (Windows 11 build 26200, one 2880 by 1800 display at 200%). The plan is [docs/engine.md](../../docs/engine.md) › Milestones.

## The layout test

M2's first step was the smallest thing that could answer the plan's two open questions in the real engine window. The answers decided the layout, which is written up in [docs/engine.md](../../docs/engine.md) › The Windows layout.

| Question | Answer | Screenshot |
|---|---|---|
| Does GPUI's DirectComposition surface work in a child HWND of the engine's Views window? | Yes | [child HWND](screens/m2-layout-test-child-hwnd.png): the sidebar is a GPUI window made a `WS_CHILD` of the engine's HWND |
| Does it blend over the page when it is see-through? | Yes | [see-through child](screens/m2-layout-test-see-through-child.png): the page's stripes are sharp through a 40% white GPUI child |
| Does system blur apply to the command bar's window? | No | [five ways of asking](screens/m2-layout-test-system-blur.png): every one is a flat fill with no variation across a striped page |

The blur GPUI asks Windows for (the undocumented accent policy) draws solid black on this Windows build. A plain Win32 window that asks the same way gets the same black, in a GDI screen copy and through Desktop Duplication, so it is Windows and not GPUI or the engine. Windows 11's documented backdrop gave a flat grey. The merged `windows/gpui-a` branch says its command bar has "DWM acrylic blur"; it uses the same call, so it has none either.

So overlays are see-through GPUI child windows, and the engine blurs the page under them in Chrome's own compositor.

## The stack sample

Tool: `cdb -pv` (non-invasive attach) from the Windows SDK, printing the main thread with `~0 kc`. `chrome.dll.pdb` has public symbols even at `symbol_level = 0`, and the UI library was built with line tables for this (`target/symbols`).

Idle:

```
win32u!NtUserMsgWaitForMultipleObjectsEx
chrome!base::MessagePumpForUI::WaitForWork
chrome!base::MessagePumpForUI::DoRunLoop
chrome!base::MessagePumpWin::Run
chrome!base::sequence_manager::internal::ThreadControllerWithMessagePumpImpl::Run
chrome!base::RunLoop::Run
chrome!content::BrowserMainLoop::RunMainMessageLoop
```

While the sidebar scrolls, GPUI is drawing a frame, called from Chromium's pump:

```
jaal_ui!gpui::window::Window::draw
...
jaal_ui!gpui::platform::windows::window::WindowsWindowInner::draw_window
jaal_ui!gpui::platform::windows::window::WindowsWindowInner::handle_paint_msg
jaal_ui!gpui::platform::windows::window::WindowsWindowInner::handle_msg
jaal_ui!gpui::platform::windows::window::window_procedure
USER32!CallWindowProcW
...
win32u!NtUserDispatchMessage
chrome!base::MessagePumpForUI::ProcessMessageHelper
chrome!base::MessagePumpForUI::ProcessNextWindowsMessage
chrome!base::MessagePumpForUI::DoRunLoop
chrome!base::MessagePumpWin::Run
```

No sample has `gpui::platform::windows::platform::WindowsPlatform::run`, GPUI's own loop. Most scrolling samples catch the main thread waiting in the pump between frames, so the script samples until one lands in GPUI's code (the fourth, in the last run).

## Not checked

Neither can be shown on this laptop without a person or more hardware.

- **IME.** No input method is installed: the only keyboard is US English. The engine blurs Chrome's input method while a GPUI view has focus, so that an IME composes into GPUI and not into the page, but nothing has run that path. To check: add Japanese (Microsoft IME) in Settings › Time & language › Language & region. Start jaal on a page with a text field. Click the field, switch to the IME (Win+Space), type `nihongo` and press Space then Enter: 日本語 should appear in the page, with the candidate window next to the caret. Press Ctrl+L, type `nihongo` again: the composition should appear in the sidebar's address field, not in the page. Press Ctrl+K and do the same in the command bar.
- **Mixed DPI.** There is one monitor. GPUI's child windows take their scale from the parent when it changes monitors (`WM_DPICHANGED_AFTERPARENT`); that code has never run. To check: connect a second monitor and set its scale to a different value from the laptop's (Settings › System › Display). Start jaal, open the command bar, and drag the window so that it crosses onto the other monitor and then sits fully on it. On each monitor the sidebar should be 236 DIPs wide with sharp text, the page should start where the sidebar ends, and the command bar should be centred over the page.

Also not checked: light and dark were both looked at (the system is dark, the acceptance run forces light), but only the light theme goes through the acceptance run.

## Not done in M2

- The exe and libraries keep Chrome's names, as in M1.
- A crashed tab is blank: Chrome's sad tab is off (see the Webium audit in `docs/engine.md`) and the `tab_crashed` event is M4.
- Favicons are letter tiles. They cross the API as image IDs later.
- A security prompt doesn't close an overlay that covers it yet, because jaal has no such prompts yet.
- A GPUI overlay can't reach past the main window's edge. A menu near the edge will need an owned pop-up, which gets no blur.
- The top resize border is missing over the sidebar: the sidebar's window covers it. The other three borders, and the top border over the page, resize the window.
- Windows 11's snap layouts don't appear when the pointer rests on the maximize button, because the app draws that button. Dragging to a screen edge snaps as usual.

## Bugs found on the way

- **Every typed character arrived twice** in a GPUI field. GPUI's own loop never calls `TranslateMessage`; GPUI translates a key itself when nothing handled it. Chromium's loop translates every message before dispatching it. Embedded mode now never translates, and takes the queued `WM_CHAR` back out when GPUI handled the key.
- **`chrome://webui-browser` crashed the browser.** jaal answers Webium's check without its flag, which also made Webium's own page loadable, and that page expects Webium's window. Found by the audit, fixed with a one-line guard.
- **Tab-modal dialogs sat 6 DIPs off the page's centre** and poked above its top edge. M1's dialog host measured from the window's outer frame, which includes the sizing borders.
- **The app never quit after its window closed.** The sidebar handled that event, and the sidebar is a child of the window, so it was already gone.
- **The mouse wheel did nothing over the sidebar** while a page had keyboard focus. Windows sends the wheel to the focused window, not the one under the pointer.
- **`windowsx.h` renames `IsMinimized` and `IsMaximized`** with macros, which broke the window class's own methods of those names.
- Two traps in the test helper: PowerShell reads an argument like `-12` as a parameter name, and its variable names ignore case, so `$c` was the script's `$C` parameter.
