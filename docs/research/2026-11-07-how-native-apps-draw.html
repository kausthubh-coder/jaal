How native apps draw, and where a Chrome page fits

A desktop app is one loop that waits for events and paints frames. The hard part of a browser is that two painters (your UI and Chrome's page) and two loops (your toolkit's and Chromium's) must share one window and one thread.

1. The main loop

Every desktop app has one main thread. It runs one loop until the app quits. On the Mac, the app's single NSApplication object runs it ([NSApp run]). On Windows, it is a GetMessage / DispatchMessage loop. Click a tab in the fake app, or step through.

frame budget: 16.7 ms at 60 Hz · 8.3 ms at 120 Hz

The key rule: the call that starts the loop does not return until the app quits. Whoever calls it first owns the thread for good. A second framework that also calls "run" never gets to start.

2. Who paints the pixels

There are three ways a toolkit gets pixels on screen. In all three, the OS compositor has the last word: WindowServer on the Mac and DWM on Windows take every window's pictures and combine them into what you see.

A. OS views

Your codeReact Native, SwiftUI, AppKit, WinUI
↓ "make a view here"
The OS draws real viewsMac: NSView, each with a Core Animation layer · Windows: WinUI
↓ many layers
The OS stacks them

B. Your own painter

Your codeGPUI, WarpUI, iced, zigui, Flutter
↓ draws every pixel itself
One GPU picture per windowMetal on Mac · DirectX or Vulkan on Windows
↓ one layer
The OS sees one flat image

C. A browser engine paints

Your codeHTML/CSS: Electron, Tauri, web UI in Chromium
↓ engine lays out and paints
The engine's compositorChromium's (viz), or WebKit's
↓ its layers
The OS shows the result
A browser adds a second painter: Chrome paints each web page itself, into its own view. Your UI and the page only overlap freely when one compositor stacks both.

That is why React Native (way A) and a web UI in Chromium (way C) can draw over a page: Core Animation stacks both on the Mac, and Chromium's compositor stacks both in the web UI. GPUI (way B) hands the OS one flat image, so a page view placed in the window lands on top of it.

4. One loop, two frameworks

Chromium must own the loop: Chrome's code assumes its own loop and its own app class, BrowserCrApplication. So GPUI has to run inside it. Step through how.

Chromium
GPUI

I read GPUI's code for this. On the Mac it queues main-thread work on the system's main queue (DispatchQueue::main() in crates/gpui_apple/src/dispatcher.rs). On Windows it posts window messages (PostMessageW in crates/gpui_windows). Any running loop processes both, Chromium's included. What's left is a focused fork of gpui_macos and gpui_windows:

  1. Skip GPUI's run(). Start GPUI from Chromium's startup callback, the way Ardia starts React Native.
  2. On the Mac, drop GPUI's own app class, GPUIApplication (crates/gpui_macos/src/platform.rs, line 67). Only one app class can exist, and Chromium's wins. Move GPUI's one per-app pointer to a global, and add its few event hooks to Chromium's class.
  3. On Windows, nothing else: Chromium's message pump already delivers GPUI's window messages.

7. Web UI in Chromium vs Loka

Loka already had a web UI in Chromium: its sidebar is a built-in page, chrome://loka-sidebar.top-chrome, inside Chrome's own window. The new idea changes three things.

Loka

  • Keeps Chrome's own browser window and hides parts of it (a "sidebar-only layout" patch).
  • The sidebar bundle is packed into the browser's resource files (paks). A UI change means bun run webui:build, then a Chromium rebuild.
  • Every agent needs the build checkout, C:\src\loka.
  • Gets Chrome's find bar, fullscreen, bubbles and side panel for free.
  • Windows only so far.

The new idea

  • Strips Chrome's window UI, as Ardia does. A small Views host shows the UI page and the page views.
  • The UI loads from a folder, or a dev server while you work, so a UI change needs no rebuild. (My design, not yet proven.)
  • The engine is a prebuilt download, so agents doing UI work need no Chromium tree.
  • Has to rebuild the find bar, fullscreen and prompts, Ardia's cost list.
  • Mac and Windows from day one.

What a web UI costs, compared with GPUI

  • One extra renderer process for the UI page. Its memory cost isn't measured yet.
  • A click crosses processes. It goes from the browser process to the UI's renderer and back. GPUI handles it on one thread.
  • Speed depends on discipline. A light framework (Lit, as Loka uses, or Solid) and a speed budget keep it fast. Edge got 42% faster by dropping React.
  • Less native by default. Blur needs a transparent page over the OS material. That is untested.
  • Gains: overlap for free, one loop, Chrome's popups attach to the window, and agents test the UI with the same CDP tools they use on pages.

8. The plan

The engine is the same whichever UI wins, so build it first. Then settle the UI with measurements, not opinions.

  1. Engine, like Ardia's. Helium plus a small layer that runs Chrome tabs and profiles with no Chrome window UI, behind a plain C API. Build it per platform: the Mac mini overnight, Windows on Depot or the laptop. Publish each build as a download, so UI work never needs the Chromium tree.
  2. Bake-off: one tiny browser, built three ways. Sidebar, one live page, a ⌘L command bar with a shadow over the page, and a tab you can drag into the page.
    • Web UI in Chromium (thin Views host).
    • GPUI inside Chromium's loop, with fix A overlays.
    • GPUI with fix B (page as texture), Mac first.
  3. Measure each on Mac and Windows. Cold start, memory with 10 tabs, tab switch time, sidebar scrolling with 5,000 rows, dropped frames while resizing, and idle CPU. Compare against plain Helium.
  4. Look at them side by side. You judge the polish.
  5. Pick the winner and build the Arc layer on it: spaces, pinned folders, Glance, command bar, auto-archive, then sync and updates.

My bet before the numbers: GPUI with fix A wins on speed and polish, and the web UI wins on simplicity. The bake-off decides.
